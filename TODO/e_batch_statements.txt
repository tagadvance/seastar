CONCEPT: BATCH statements and additional request/query processors
PRIORITY: 5 (common driver usage; currently unhandled)

SOURCE COMMENTS (now removed):

- SeaStarCqlRequestHandler.java:70  "batch statement" (// TODO)

CURRENT STATE:
handle() only accepts SimpleStatement and SeaStarBoundStatement, extracting a single query
string. BatchStatement (driver) and Cassandra's BatchStatement.Raw parse tree are not handled,
so batched writes fail.

WHAT REAL CASSANDRA DOES:
A BATCH groups multiple INSERT/UPDATE/DELETE statements applied together (LOGGED/UNLOGGED/COUNTER).
Ordering and atomicity semantics differ by batch type, but for an in-memory fake, applying each
child statement in sequence under the table locks is a reasonable first cut.

IMPLEMENTATION PLAN:
1. In handle(), detect driver BatchStatement and iterate its child statements, dispatching each
   through the existing handler pipeline.
2. Add a BatchHandler for Cassandra's BatchStatement.Raw path when a batch arrives as a parsed
   CQL string: unwrap the child statements (Reflections) and dispatch each to the matching
   CqlHandler.
3. Register BatchHandler in the CqlHandlerRegistry (see concept (k) about where that lives).
4. Fidelity: reject SELECT inside a batch, and mismatched batch types, with the same
   InvalidQueryException a live cluster throws.

DEPENDENCIES: benefits from concept (k) registry relocation but does not require it.

FOLLOW-UP (deferred, documented as a known limitation in BatchHandler's javadoc):
Batches are currently applied child-by-child and are neither atomic nor isolated. Real Cassandra
validates every child up front and rejects the whole batch before writing anything, so an invalid
statement leaves the store untouched; here a child that fails partway through leaves the earlier
children already applied. Fix if/when it matters. Preferred approach: snapshot-and-restore scoped
to the affected tables - resolve the tables each child targets, acquire their write locks in a
stable order (deadlock-safe, reentrant with the child handlers), deep-snapshot their row state,
run the children, and restore the snapshots on any exception. Holding the locks for the whole
batch also buys isolation. This needs a new table primitive (VolatileTable mutates rows in place
and only exposes an immutable column-definition snapshot() today). Frame it as best-effort
atomicity, not a general transaction: Cassandra's real model is atomic-but-not-isolated with no
rollback, so a true rollback transaction would over-model the real thing.
