CURRENT STATE:
handle() only accepts SimpleStatement and SeaStarBoundStatement, extracting a single query
string. BatchStatement (driver) and Cassandra's BatchStatement.Raw parse tree are not handled,
so batched writes fail.

WHAT REAL CASSANDRA DOES:
A BATCH groups multiple INSERT/UPDATE/DELETE statements applied together (LOGGED/UNLOGGED/COUNTER).
Ordering and atomicity semantics differ by batch type, but for an in-memory fake, applying each
child statement in sequence under the table locks is a reasonable first cut.

IMPLEMENTATION PLAN:
1. In handle(), detect driver BatchStatement and iterate its child statements, dispatching each
   through the existing handler pipeline.
2. Add a BatchHandler for Cassandra's BatchStatement.Raw path when a batch arrives as a parsed
   CQL string: unwrap the child statements (Reflections) and dispatch each to the matching
   CqlHandler.
3. Register BatchHandler in the CqlHandlerRegistry (see concept (k) about where that lives).
4. Fidelity: reject SELECT inside a batch, and mismatched batch types, with the same
   InvalidQueryException a live cluster throws.

DEPENDENCIES: benefits from concept (k) registry relocation but does not require it.
